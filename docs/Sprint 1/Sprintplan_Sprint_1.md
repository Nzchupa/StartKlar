## 1. Sprint-Ziel

> **Am 19.11. stellen wir einen vollständigen, priorisierten Anforderungskatalog mit Use-Case-Diagramm vor. Bis 26.11. ist der MVP-Umfang mit dem Stakeholder abgestimmt und wir zeigen einen ersten Prototyp (Klick-Entwurf + lauffähiges Projektgerüst).**

Die drei Fragen des Sprint Plannings (VL3):

- **Warum ist der Sprint wichtig?** Ohne abgestimmte Anforderungen bauen wir am Bedarf vorbei. Der Katalog ist Prüfungsleistung (19.11.) und Grundlage für alle weiteren Sprints.
- **Was müssen wir tun?** Anforderungen bereinigen, prüfbar machen, nach MoSCoW priorisieren, MVP abgrenzen, präsentieren, mit dem Stakeholder verhandeln, Prototyp vorbereiten.
- **Wie erledigen wir es?** Jede Aufgabe wird ein GitHub-Issue. Jede/r wählt Aufgaben selbst (unabhängig von der Rolle), arbeitet in einem eigenen Branch und öffnet einen Pull Request.

## 4. Definition of Done

Eine Aufgabe ist erst **fertig**, wenn:

- [ ] das Ergebnis im Repository liegt (über Branch + Pull Request, nicht direkt auf `main`),
- [ ] mindestens eine andere Person den Pull Request geprüft hat,
- [ ] das Akzeptanzkriterium aus der Tabelle erfüllt ist,
- [ ] abgabepflichtige Dokumente zusätzlich in der Nextcloud liegen,
- [ ] die Arbeitszeit in der eigenen Zeiterfassung eingetragen ist,
- [ ] das Issue geschlossen ist (`Closes #…` im Pull Request).

## 7. Risiken

| Risiko | Gegenmaßnahme |
| --- | --- |
| Technikentscheidung zieht sich hin → kein Prototyp am 26.11. | Entscheidung spätestens im Check-in am 18.11. treffen; Wireframes als Plan B für die MVP-Vorstellung |

| Ausfall eines Teammitglieds | Puffer einplanen, Aufgaben im Check-in neu verteilen |
| Anforderungen zu umfangreich | MVP klein halten, Rest als Should/Could in spätere Sprints |
